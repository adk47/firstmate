This reference covers Muso's data model and the query patterns over it, with
context on MongoDB and PostgreSQL access. Use it to understand how the
catalog fits together; use `SKILL.md` to actually run something.

## Key Concepts

**Athena** *(retired 2026-04-25)*: the AWS-managed Presto fork Muso used to query S3 until the OVH migration. Its role — SQL over the data lake for statistical analysis — is now filled by **Trino**, which shares the same Presto SQL dialect, so queries written for Athena generally run unchanged.

**Work Group** *(Athena-era, gone)*: an Athena-side grouping for queries and access control; `primary` held historical queries and teams used their own, e.g. 'growth dev'. Trino has no equivalent — access is not segmented this way.

**Saved Queries**: four years of accumulated queries, many outdated. The Athena-hosted ones went away with Athena; the surviving set is checked into the repo at `skills-all/muso-query-writer/saved-queries/`.

**Data Lake**: object storage holding raw and processed data, queried through Trino. (Athena-era this was S3; the storage moved to OVH with everything else.)

**Snapshot**: Point-in-time copy of database data exported to the data lake for analytical querying. MongoDB uses weekly full snapshots with daily delta updates; PostgreSQL snapshots vary by table.

**Catalog Entity**: Unified, canonical representation of a music industry entity (profile, track, release) created by merging multiple raw source records.

**Raw Entity**: Source-specific representation of an entity as captured from external platforms like Spotify, containing platform-specific IDs and metadata.

**Credit**: Relationship between a profile (person) and a track or release, including specific roles like producer, engineer, or artist.

**Soft Delete**: Deletion pattern where entities are marked as deleted rather than physically removed, preserving data for potential restoration.

**Calculated Table**: Pre-aggregated data table generated by daily platform processes, stored in the data lake and queryable via Trino.

## Architecture

### Data Storage Layers

Muso's data architecture consists of three primary storage systems:

1. **MongoDB (Industry DB)**: Graph database storing core catalog entities (profiles, tracks, releases, credits) optimized for search and sorting.

2. **PostgreSQL (Stats DB)**: Relational database storing pre-calculated analytics and metrics, optimized for high-computation tasks. *Runs on OVH Postgres (Crunchy PGO PostgresClusters, `databases` namespace). Athena-era this was AWS Aurora `platform-stats-prod`, torn down 2026-05-31 — **there is no Aurora; do not reach for it**.*

3. **Data Lake**: Raw and processed data files organized by source and date, queryable via Trino.

### Query Access Patterns

```text
Query need?
  |
  +-- Real-time / up-to-the-minute --> Production DBs
  |       |--> MongoDB         --> Specific entity lookup
  |       `--> OVH Postgres    --> Pre-aggregated metrics
  |
  `-- Historical / analytical --> Data lake + Trino  (was S3 + Athena)
          |--> Raw snapshots     --> Statistical analysis
          `--> Calculated tables --> Time-series queries
```

**Team Ownership**:
- Platform team: Manages data pipelines, Airflow, snapshot processes
- Catalog team: Maintains entity data model, credit relationships
- Infrastructure team: Manages database access and query-engine configuration (Athena-era: Athena config; now the OVH Trino cluster)
- Growth team: Analytics consumers (Athena-era they had their own 'growth dev' work group; no Trino equivalent)

### Data Flow

1. **Capture**: External platforms scraped/fetched by Analytics Worker
2. **Ingest**: Raw data stored in the data lake as partitioned JSON files
3. **Process**: Spark jobs combine and transform data via Airflow pipelines
4. **Snapshot**: Weekly MongoDB dumps and daily deltas exported to the data lake
5. **Query**: Trino provides the SQL interface over the data lake (Athena-era: Athena over S3)

## Query Patterns

### Pattern 1: Querying Streaming History

**Use Case**: Analyze track streaming data across platforms

```sql
SELECT 
    track_id,
    source,
    SUM(streams) as total_streams,
    DATE_TRUNC('month', date) as month
FROM calc_analytics_history
WHERE date >= DATE '2025-01-01'
    AND source IN ('spotify', 'youtube', 'soundcloud', 'shazam')
GROUP BY track_id, source, DATE_TRUNC('month', date)
ORDER BY total_streams DESC
```

**Explanation**: The `calc_analytics_history` table combines streaming data from multiple sources (Spotify, Shazam, SoundCloud, YouTube) and is partitioned by date. This table is regenerated daily by platform processes reading JSON files from the data lake.

**Performance Notes**:
- Original source JSON files are deleted after 30 days, but processed table partitions are retained
- Use date filters to limit partition scanning
- Presto documentation applies for function reference

### Pattern 2: Joining Catalog and Raw Entities

**Use Case**: Link catalog tracks to their source platform IDs

```sql
SELECT
    ct._id AS catalog_track_id,
    ct.title,
    r.rid AS raw_id,
    split_part(r.rid, ':', 1) AS source
FROM hive."platform-industry-bi-prod".matvw_catalog_track ct
CROSS JOIN UNNEST(ct.raw_recording_ids) AS r(rid)
WHERE ct.release_timestamp >= to_unixtime(current_date - interval '365' day) * 1000
  AND NOT ct.is_deleted
LIMIT 100
```

**Explanation**: Catalog tracks store raw recording IDs as a list to establish relationships with source data. Use `CROSS JOIN UNNEST` (Presto/Athena syntax) to unnest the array. Raw IDs follow format `source:id` (e.g., `spotify:abc123`).

### Pattern 3: Credit Analysis with Embedded Data

**Use Case**: Find all tracks where a profile has a specific role

```sql
SELECT
    t._id AS track_id,
    t.title,
    p.profile.role,
    p.profile.profile_id
FROM hive."platform-industry-bi-prod".matvw_catalog_track t
CROSS JOIN UNNEST(t.profiles) AS p(profile)
WHERE p.profile.profile_id = 'TARGET_PROFILE_ID'
    AND p.profile.role = 'producer'
    AND NOT t.is_deleted
ORDER BY t.popularity DESC
LIMIT 100
```

**Explanation**: Credits are embedded inside each track to avoid complex joins when filtering by popularity or release date. The `profiles` array contains credit information with profile IDs and roles. Use `CROSS JOIN UNNEST` (Presto/Athena syntax) to unnest the array.

**Why Embedded**: This denormalization optimizes for common query patterns that need to sort tracks by metadata while filtering by credits.

### Pattern 4: Accessing Pre-calculated Metrics

**Use Case**: Retrieve profile streaming metrics by role and period

```sql
SELECT 
    profile_id,
    role,
    period,
    total_streams,
    track_count
FROM profile_track_streams_by_period_and_role
WHERE profile_id = 'target_profile_id'
    AND period >= '2025-01'
ORDER BY period DESC, total_streams DESC
```

**Explanation**: Metrics are pre-calculated to avoid slow real-time joins between MongoDB and streaming data. These tables are stored in the Stats DB (OVH Postgres; Aurora pre-migration) and also snapshotted to the data lake.

**Access Pattern**: Stats DB has a separate schema granting direct access to Core Backend API for real-time queries.

### Pattern 5: Handling Soft Deletes

**Use Case**: Query only active (non-deleted) entities

```sql
SELECT
    _id,
    title,
    release_date
FROM hive."platform-industry-bi-prod".matvw_catalog_track
WHERE NOT is_deleted
LIMIT 100
```

**Explanation**: Primary entities (track, album, profile) are always soft deleted, meaning they're marked as deleted rather than removed. Always filter on `is_deleted = false` (or `NOT is_deleted`) unless you specifically need to include deleted records.

**Note on Credits**: When a raw credit relationship is soft deleted, the credit is hard deleted from the entity's embedded profiles array.

|------------|-------------------|---------|

### Performance Considerations

**MongoDB Limitations**:
- High IOPS cost for heavy insertion tasks
- IOPS limits strain analytics and filtering operations
- Better suited for entity lookup than aggregation

**Data-lake Query Best Practices** (Athena-era advice; still true on Trino):
- Always use partition filters (date, source) to limit scanning
- Saved queries may be outdated—verify before reusing
- Snapshot process can take up to 16 hours for MongoDB due to non-scalable integration
- Verify table and column names with `SHOW TABLES` / `DESCRIBE` before relying on any name in this file

**Stats-DB (PostgreSQL) Advantages**:
- Better suited for high-computation analytics tasks compared to MongoDB
- Used for pre-aggregated collaboration data

## Troubleshooting

### Query Access Issues

**Symptom**: `muso query` fails to reach the cluster, or returns an auth error

**Resolution**:
1. Run from node-8 — that is where the runner and its cluster access live
2. Check the Trino endpoint in `SKILL.md` (`trino.data-processing.svc.cluster.local:8080`)
3. Escalate to H-DevOps for cluster-side access

> The Athena-era answer here was "verify work group permissions / switch to
> 'growth dev' / ask infrastructure for broader permissions". **All three are
> dead** — there is no Athena console and no work groups. Never route someone
> to request Athena access.

### Missing Data in Snapshots

**Symptom**: Expected table not found

**Resolution**:
1. Probe first — `SHOW TABLES FROM ...` / `DESCRIBE`. Documented names, including the ones in this file, drift and are frequently wrong
2. Check if the table is excluded from snapshots (very large tables sometimes are)
3. Contact the platform team for snapshot additions
4. Consider accessing via production database if real-time data is needed

### Slow Query Performance

**Symptom**: Queries timing out or taking excessive time

**Resolution**:
1. Add partition filters (date ranges)
2. Verify you're not scanning deleted source files (>30 days old)
3. Consider using pre-calculated tables instead of raw data
4. Check if MongoDB access would be more appropriate for specific ID lookups
