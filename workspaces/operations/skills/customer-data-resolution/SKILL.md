# Customer data resolution

## Procedure

1. Re-read the authoritative customer conversation and resolve the current profile, playlist, track, or other entity by both ID and display name; finish when the reported symptom and latest customer expectation are explicit.
2. Record live UTC state and a measurable pass condition. If Intercom IDs differ, use the owned populated profile; never infer a merge.
   - Stream screenshot: extract scope, period, and numeric historical count; compare authoritative total, freshness, processing, credit direction, and audit. If mismatched, file one `data_verification` with expanded `B`/`M` numbers; keep open and change no source links before verdict.
   - Disputed merge: use the deleted-inclusive list; direct loser GET may redirect and hide merge metadata. Require loser `merged.mergedToId` = survivor plus deletion. If profile roles are correct but album artist/raw credits point to another external artist, preserve it and route a distributor remap.
   - Plaque order by email: exact-normalize email, join all orders, separate paid/processing/shipped orders from unpaid `NEW` drafts, and report paid order number, ID, creation time, and internal status. Call processing internal unless vendor state was read.
   - Missing credit: resolve the exact external track, then query profile+track+role; prior tickets and assumed self-service submission are not proof. If pending is empty but authoritative raw-credit rows corroborate the profile name and role, an allowlisted requester may use the audited per-track add with `{"credits":["producer"]}`—never singular `role`. Canary one and require exact track/role read-back before the rest; finish only at N/N. Otherwise hand off with IDs, URL, pass condition, and SLA.
   - Missing accepted-credit metadata: resolve track, field, and non-pending source into one bridge request. Never resubmit or trigger capture/enrichment; require field read-back.
   - Screenshot dispute: OCR attachments; corroborate IDs, title, authors, profile, and raw identities. Route same-name mismatches as one `data_verification`; require bilateral read-back.
   - Track analytics: verify credit, track ID, and sources. With no Spotify rows, run one authorized enrichment. With Spotify stale-pending and zero/no first stats, route targeted capture; never remove/re-add. Missing YouTube requires its official URL. Finish at `pending=false` with a real count.
   - Label-release dispute: compare `profile-labels` with fully paginated credits grouped by normalized label and distinct release ID. Route mismatches as one `data_verification`; never edit credits to force display.
   - Artwork dispute: compare public Muso and Spotify images and identify primary versus merged Spotify ID. Route source materialization as one track-pinned `data_verification`; never remove/re-add or trigger capture. Require the expected public image on the profile, backend role attachment, and filtered-page visibility before sending a resolved update; an attached role does not prove it renders and a materialized source does not prove the image changed.
   - Claimed profile showing “0 claimed”: triangulate claim, workspace associations, and roster seats; a processed claim lacking either is a linkage mismatch.
   - Claimed profile absent from app/Add Credits: compare claim, workspace links, same-name candidates, and tracks; never infer duplicates. If unresolved, file one profile `data_verification`; advise no reclaim/merge before verdict.
   - Stage/legal-name mismatch: obtain official URLs or ISRCs before identity verification; never mutate title-only matches.
   - TikTok “Original sound” without a URL: derive `musicId` and verify owner plus `videoCount`; otherwise request its Share URL.
3. For credit cleanup spanning profiles, resolve every profile by ID, display name, claimed state, and entity type; enumerate the exact profile-role-track rows and inspect their raw source identities. Treat credit removal, raw-source unlinking, profile merging, and profile deletion as separate outcomes. Do not merge an unclaimed artist identity into a claimed organization merely because their names overlap. Before merging several claimed person profiles, list all claim rows for the survivor and every loser in one unfiltered, fully paginated read. Proceed only when the survivor has a processed claim and every loser claim belongs to that same workspace. Revert every loser claim, verify each claim reads back as `reverted`, and re-read the profiles to confirm the survivor remains claimed before running the merge; never leave one loser claim active for the merge to transfer implicitly. For color-coded credit sheets, read XLSX formatting and match removal rows to the paginated live list by normalized title plus artist; never use row position. Deduplicate repeated rows to track IDs and stop on unresolved, ambiguous, or unexpected Primary Artist matches. Keep Record Label profiles with label-role credits separate from artists; route wrong label metadata to the distributor. When one case contains both a true duplicate and a same-name different artist, merge only the customer-confirmed duplicate and remove only the exact misassigned rows while preserving legitimate releases. Dry-run a merge and require `verified`, then verify direction and deletion; if status is missing, do not retry—prove `mergedToId`, loser deletion, survivor activity, and absorbed raw identities from the live deleted-inclusive list. Clarify whether a brand/work-for-hire dispute means a false credit or wrong identity, and unlink raw sources when needed to prevent re-ingestion. For unsupported user-approved credits, compare `addedBy`, `credit_requests`, and raw identities, then remove only enumerated rows using one canary and live absence after each delete. A removal preview proves identity, not writability; Primary Artist credits may still be refused on apply. If the customer owns the profile, the exact track/profile pair has only the disputed roles, and an allowlisted ops requester directs resolution, re-read after any refused apply, pre-audit the enumerated pairs, and call each per-track DELETE once with `?force=true`—it removes all roles for that pair. Require every requested title absent in profile and track read-back and confirm the profile count changed by the expected amount, then rebuild collaborators before updating the customer. If extra roles, an error, or unknown state exists, stop without retry, re-read, and ticket with IDs, roles, count, pass condition, and SLA; keep open until absence is verified. Keep broader audits on their existing bridge request ID and finish only when every row has an explicit disposition. For a single-track same-name misattribution, identify the exact track by ID and artist, read the incorrect and intended profiles by ID and claimed state, and confirm the incorrect profile holds exactly the disputed role while the intended profile does not. Add the exact role set to the intended profile first with the per-track endpoint body `{"credits":["Role", ...]}` (one array containing every expected role), then require an immediate read-back showing exactly 1 matching track with every expected role before deleting anything. Then delete only that role set from the incorrect profile and require bilateral read-back: 0 matches on the incorrect profile and exactly 1 matching track with the expected roles on the intended profile. At the bulk-delete threshold, pass the allowlisted requester in `--confirmed-by`, the exact target-set decision in `--approval-msg-id`, and required author/channel fields. Send the completion update only after both conditions pass.
4. Find the verdict or issue before opening work. Route its request ID, entity ID/name, measured delta, and customer-visible pass conditions; acknowledgment is not resolution. If silent or missing, paginate for that mailbox marker, keep its URL, and chase only that ID. Attach a push or bounded watch, then yield. On heartbeat or timeout, resume from the exact request’s authoritative status; ignore unrelated or superseded helper-process failures. After reported repair, verify the served aggregate and every named sentinel. Finish with verified resolution or explicit open owner/status.
5. When remediation lacks a gated operation, create a follow-up ticket with entity IDs, evidence, outcome, and read-back condition; require a concrete ID and SLA. To append to a known ticket, use an ID-addressed update path; never hide `existing_ticket_id` in create-ticket details. Require the returned ID to equal the known ID, or stop and report the duplicate as an end-state mismatch.
6. Send customer updates only when explicitly requested. Resolve the Intercom conversation ID and freshly read the latest messages; if the UI is signed out, use the authenticated read-only `/conversations/<id>?display_as=plaintext` response and retain state, timestamps, types, authors, and bodies. State only confirmed facts, never claim an unverified fix, and quote the support SLA. If an engineering owner is tagged but has not returned verified guidance, send the confirmed interim workaround without blocking, say specialist review is pending, keep the case open, and follow up with the later result. Do not repeat troubleshooting the customer already completed unless the owner requests a new diagnostic. Validate through the approved customer-reply wrapper and require a concrete part ID. After interruption, recover conversation-ID-named artifacts and the prior wrapper result; otherwise re-read Intercom and match the exact outbound body before resending. A pre-write audit without a part ID or matching message is unknown; escalate if authoritative read-back is unavailable.
7. Re-read the live customer-visible surface after the workflow. For an internal summary-and-resolution request, post an Intercom internal note addressed to the requester—not a customer reply—with the symptom, measured state, action taken, proof, and open/closed disposition. When the fix is verified and the customer’s latest message is only thanks or confirmation, state that no further customer reply or catalog action is needed and recommend closing the conversation; do not broaden the resolution into a merge or reopen older requests without separate evidence. Close only when the pass condition is met; otherwise report the exact mismatch (for example, 0/1 corrected), keep the case open, and escalate the unresolved end state with the ticket and conversation evidence.

## Verification

A completed resolution includes either live proof that the requested state landed or an explicit open status with a concrete owner, ticket ID, SLA, customer-reply ID, and failed read-back count. A successful API response or created ticket alone is never proof that customer-visible data changed.
