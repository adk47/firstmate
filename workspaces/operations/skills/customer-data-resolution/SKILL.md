# Customer data resolution

## Safety rules (non-negotiable)

These bind every case, including every playbook under `references/`, and win over any playbook text. Keep them in this file; put new case learning in the matching `references/` file.

- Disputed merge: require deleted-inclusive proof that each loser is deleted and points to the survivor; preserve distinct raw identities and route distributor remaps.
- Keep removal, raw unlinking, merge, and deletion separate.
- Profile merge: separate entity types and labels. Require a processed-claim survivor, complete ownership proof for every loser, and inventory review excluding unrelated, group, or mixed-credit profiles. Revert loser claims and verify them unclaimed; dry-run loser → survivor, submit once, then prove forward direction, loser deletion/redirect, absorbed identities, credit floor, and survivor claim. Capture pending request IDs before merging; afterward require survivor `profileId`, approve only those IDs, and reconcile statuses and notice count. If status is unavailable, prove state instead of retrying. Merge-scope anchor: `references/credit-cleanup.md`.
- Album-role/artist dispute: build an exact profile+track+role manifest (compare roles and `addedBy`) and never remove a whole profile. For same-name disputes, compare the profile’s linked source IDs with the track’s complete raw-credit identities; a displayed role with zero source linkage is unsupported when none of those IDs appears; report misattribution evidence, not a cause. For mixed catalogs, inspect raw mappings, source credits, and audit history; route identity splits through one track-pinned verification request. Resolve only after the correct artist/roles are present, disputed identities/roles absent, and protected roles unchanged. Same-name source-ID procedure: `references/credit-cleanup.md`.
- “0 claimed” or missing from app/Add Credits: compare claims, workspace links, roster seats, same-name candidates, and tracks; never infer duplicates. A processed claim without workspace linkage is a mismatch; file one profile verification and advise no reclaim/merge.
- Two-account name mismatch: resolve both users, workspaces, claims, access, and aliases. If the paid workspace can write the canonical profile, create no claim. Rename only that ID; prove credits, access, admin state, and public title. Say the claim moved only when its workspace changes live.
- Claimed-profile rename: prove ownership; record names, claim, and credit count. Audit, then submit one name-only `PUT /admin/profile/:profileId`. Reply through the approved wrapper only after admin and support reads show the target name, retained claim, and unchanged credits; record its part ID.
- Missing accepted-credit metadata: route track, field, and source once; never resubmit or capture; require read-back.
- Publisher-credit evidence review: for bulk catalogs, request CSV/XLSX rows with title, artist, release, role, ISRC, and available ISWC, IPI/CAE, writer/publisher, UPC/DSP URL. Compare proof with every live pending request. ISRC links a recording but does not prove publishing ownership; require exact recording/work linkage and ownership share. Inspect duplicate normalized titles separately, leave unmatched recordings pending, and update the customer only after live read-back.
- Profile role-tag dispute: compare headline chips, descriptor, and ranked parent roles; verify display truncation before pinning Artist. An unchanged recompute is Product/Web work, not stale data: do not refresh, replay, merge, or edit credits. Override only with approval and ordered-header read-back. For combined name-and-roles corrections, read back each field: the endpoint can accept both while persisting only the name. Treat unchanged roles as partial, never retry the ambiguous write, route exact expected/actual roles on one verification request, and tell the customer only the name is complete until roles appear live.
- MLC Audit: reconcile cover totals with detailed ISRC-row counts and summed streams; mismatches stay open. Muso credits do not prove MLC status. Resolve the profile and hand off; without identifiers/status, verify ISRC/ISWC, classification, and correction. Claim no fix before verdict.
- Legal-name privacy removal: preserve works. Check public profile, release, collaborator, and credit surfaces; record exposures; file one entity-pinned `data_verification` requiring absence from public/search-indexable Muso metadata. Keep open until live read-back.
- Artwork dispute: compare public Muso/Spotify images and primary/merged IDs. Record source, state, UTC time, and empty/pending fields; file one verification. Never remove/re-add or capture. Require public and backend proof.
- Analytics discrepancy: compare ownership, entitlement, freshness, periods, totals, and the visible surface; resolve same-title IDs first. For an inflated YouTube source, compare the stored metric with the live platform count and published date; if the stored digits encode the date rather than views, preserve the valid source, route correction of that metric plus history rebuild, and require source-level, track-total, and profile-total read-back. After removal, prove the track absent and read total plus processing state. If still wrong, update the same bridge request with IDs, delta, UTC time, and Intercom link; never move, recapture, fastlane, delete again, or merge an ambiguous remaster. When a live non-pending source conflicts with counters, preserve it and file one metric verification. For row-level popularity/display metadata, aggregate totals, cube readiness, and stream history are not resolution proof: read every named track’s served fields and require an exact pass count (for example, 4/4) before replying. Later alignment without verified remediation means only “not reproducible”; keep open until the customer confirms. TikTok short-link and pass-count procedures: `references/analytics-cases.md`.
- Login reset loop: identity rule: `references/intake-cases.md`; compare web/app auth, offer web, and keep open without outage claims. NFC failure: if canonical `/p/:alias` reaches the claimed profile (final 200), preserve the mapping, provide that canonical short URL for rewriting, and treat locked-tag replacement separately from legacy-host repair.

## Procedure

Playbooks live in `/opt/hydra/workspaces/operations/skills/customer-data-resolution/references/`. Read the named file there before acting on a matching case.

1. Re-read the authoritative conversation. Make one claim row per supplied link or named release, preserving message order and pairing each URL only with adjacent title/role text; never let a later title relabel an earlier URL. Resolve every row independently by ID and name, state which rows any handoff covers, and make each symptom and the latest expectation explicit.
2. Record live UTC state and a pass condition, then use `references/intake-cases.md`. If account or Intercom pointers conflict or look stale, search same-name candidates and select only the populated profile whose workspace/email proves ownership; never infer a merge or trust a bare pointer.
3. For credit cleanup, use `references/credit-cleanup.md`. Resolve exact track IDs and protected sets. Customer-owned removal needs preview and confirmation. On an unclaimed profile, an allowlisted operator may authorize per-track admin removal of the customer’s exact list from the authenticated conversation; do not require a claim first. Canary once, verify the authoritative total, then rebuild collaborators. After interruption, retry only live targets. Purges (`force` for Primary Artist) require zero authoritative credits and collaborators; ignore lagging summary counters.
4. Route IDs, pass condition, and reply authorization; “underway” is not fixed. If an Intercom URL fails bridge validation, omit the URL from evidence, retain the ID in an authenticated note, and revalidate the same request ID. Read the bridge thread and conversation parts after the last outbound. If both are silent, post one same-request `--follow-up` plus an internal open-state note; do not resend to the customer. Treat failed reads as unknown and contradictions as open without repeat writes. Finish with live proof and the reply part ID.
5. If no gated remediation exists, create or ID-update one ticket containing IDs, evidence, outcome, read-back condition, and SLA. Require the support artifact; conversation text is not proof. Conflicting returned and known IDs are a duplicate end-state mismatch.
6. For full account/profile deletion, split account deletion, profile visibility, and catalog-association/reassociation suppression. Inventory the live credits endpoint and trust its total over summary counters or stated counts. Audit each write; delete the exact account and tombstone only the owned profiles. Prove zero active users/team members, active profile `not_found`, deleted-inclusive tombstones, and canonical public 404s. Preserve catalog associations until the data owner confirms a supported removal/suppression path. Record partial completion internally and send no completion claim while any association is unverified.
7. Update customers only when asked after re-reading authenticated plaintext. Live-read deliverables; unavailable is unconfirmed. Use the standard two-business-day window. Send through the approved wrapper and require a part ID; after interruption, match the outbound body before resending. Follow `references/customer-updates.md` for legal/stage-name consolidation, invoice PDFs, streaming-unavailable questions, and app-only freezing. No case exists yet for lingering previews; do not invent guidance.
8. Verify every change live; accepted writes are not proof. For a tombstone, require deleted-inclusive presence, active absence, direct-detail `not_found`, and canonical plus cache-busted public checks. If only canonical serves hydrated data, append both URLs, cache states, UTC time, and body shapes to the existing bridge request; never repeat the delete. Report proof and disposition on the requester’s surface. Locate delayed Slack threads by Intercom conversation ID and confirm requester/history before sending. Keep mismatches open with ticket and conversation evidence.

## Verification

A completed resolution includes either live proof that the requested state landed or an explicit open status with a concrete owner, ticket ID, SLA, customer-reply ID, and failed read-back count. A successful API response or created ticket alone is never proof that customer-visible data changed.
