# Customer data resolution

## Procedure

1. Re-read the authoritative customer conversation and resolve the current profile, playlist, track, or other entity by both ID and display name; finish when the reported symptom and latest customer expectation are explicit.
2. Record live UTC state and a measurable pass condition. If Intercom IDs differ, use the owned populated profile; never infer a merge.
   - Stream screenshot: extract scope, period, and numeric historical count; compare authoritative total, freshness, processing, credit direction, and audit. If mismatched, file one `data_verification` with expanded `B`/`M` numbers; keep open and change no source links before verdict.
   - Disputed merge: inspect the deleted-inclusive list; require loser `mergedToId` = survivor plus deletion. Preserve distinct external album-artist/raw identities and route distributor remap.
   - Plaque order: exact-match email, separate paid/processing/shipped orders from unpaid `NEW` drafts, and report paid order number, ID, creation time, and internal status. Call processing internal unless vendor state was read.
   - Missing credit: resolve external track and query profile+track+role; tickets are not proof. If pending is empty and raw rows corroborate name+role, an allowlisted requester may audited-add with `{"credits":["producer"]}`. Canary one and finish only at N/N exact read-back; otherwise hand off with IDs, URL, pass condition, and SLA.
   - Missing accepted-credit metadata: route track, field, and non-pending source once; never resubmit/capture; require field read-back.
   - Screenshot dispute: OCR attachments and corroborate IDs, titles, authors, profiles, and raw identities. Route same-name mismatches once; require bilateral read-back.
   - Login reset loop: treat a stated email as a lookup clue only. Resolve IDs, confirmation/claim state, and credit count through the supported read-only owner; zero credits is not proof of loss. After the auth cutover, never retry legacy/admin reset links: confirm inbox control, direct the customer to `login.muso.ai/forgot-password`, and have them use only the newest “Auth Password Reset Requested” email. With no live tool, update one handoff with the identity caveat, evidence, pass condition, and SLA. Ask once for inbox control and a redacted post-click screenshot; keep open until access read-back.
   - Track analytics: verify credit, track ID, sources, customer-visible total, source-import watermark, calculation watermark, and reported ISRC. Fresh cube data or a rising total is not recovery when calculation is stale or the ISRC is absent. Finish only with a nonpending source, corrected total, and present ISRC.
   - Label-release dispute: compare `profile-labels` with paginated credits by normalized label and release ID; route once and never edit credits to force display.
   - Artwork dispute: compare public Muso/Spotify images and primary/merged Spotify IDs. For a pending source or empty artwork/release fields, record source ID/link, pending state, observed time, and empty fields; route one track-pinned verification immediately. Never remove/re-add, capture, or treat capture acceptance as proof. Resolve only after public image, backend attachment, and filtered-page read-back.
   - “0 claimed” or absent from app/Add Credits: compare claim, workspace links, roster seats, same-name candidates, and tracks; never infer duplicates. A processed claim missing workspace/roster linkage is a mismatch. If unresolved, file one profile `data_verification`; advise no reclaim/merge before verdict.
   - Stage/legal-name mismatch: require official URLs or ISRCs; never mutate title-only matches.
   - TikTok “Original sound” without a URL: derive `musicId` and verify owner plus `videoCount`, or request its Share URL.
3. For credit cleanup, resolve each profile by ID, name, claim, workspace, and entity type; enumerate profile-role-track tuples and raw identities. Keep removal, raw unlinking, merge, and deletion separate.
   - Album-role dispute: compare roles and `addedBy`; use an exact profile+track+role manifest, never whole-profile removal. After a lost response, recover the audit correlation and read every track before retry or customer contact; require disputed roles absent and protected provenance unchanged.
   - Profile merge: separate entity types and labels. Require a processed-claim survivor and complete claim list proving every loser is in its workspace. Revert all loser claims; verify `reverted`, losers unclaimed, survivor claimed. Dry-run and submit loser → survivor, then poll status to `verified`; require forward direction, absorbed identity, credit floor, and loser lookup resolving to survivor. Explicitly map multiple losers; never infer by name/count. Exclude unrelated/group profiles.
   - Removal list: normalize title+artist, deduplicate IDs, compare provenance, and canary one. Stop before any delete when a requested row is ambiguous: a title+artist that matches more than one live association, no association, or a different profile than the one named. Report the ambiguous rows and the pass condition instead of guessing; this refusal covers non-primary roles, which the Primary-artist collision protocol below does not. If every role on an owned profile+track pair is disputed, an allowlisted resolver may audited-delete that exact pair; otherwise remove roles only. For all-track cleanup, enumerate associations, rebuild collaborators, and require zero in admin, public credits, and no-cache HTML. If API is zero but HTML remains, file one profile `data_verification` and do not repeat absent writes.
   - Primary-artist collision: require the exact Primary Artist tracks to keep; snapshot and hash all other live Primary Artist track IDs. Remove only that role with `DELETE /admin/track/<track_id>/profile/<profile_id>/credits?force=true` and `{"credits":["Primary Artist"]}`—never delete/re-add a pair when other roles remain. Canary one. At the bulk threshold cite the allowlisted requester’s exact-set decision with `--confirmed-by`, message ID, author ID, and channel. After interruption regenerate the live remaining-set count/hash and resume only it. Finish when remaining Primary Artist IDs equal the keep set, no pre-existing non-primary role was lost, and collaborator rebuild/list reads agree; newly surfaced non-primary roles are preserved data when existing-role loss is zero.
   - Same-name collision: verify tracks, claims, roles, and hierarchy. Add missing child roles to the claimed destination before removing wrong roles. If every track is already correct there, never merge or re-add: canary-delete one exact wrong pair, verify zero wrong/one intended, remove the exact remainder, then rebuild and read both collaborator directions. Pass bulk authorization fields; update the customer only after bilateral proof.
   - Mixed-source collision: prohibit merge, whole-source unlink, and provenance-free delete/re-add. Enumerate recording+role tuples and destination/claim/workspace lineage; regenerate and hash the UUID+ISRC+role manifest immediately before writing. Require track proof for ambiguous roles and authorization naming source, destination, hash, roles, and consolidation. Apply tuple-level exclusion plus provenance-preserving re-home; verify both profiles immediately and after the next pipeline cycle.
4. Route the existing request ID, entity ID/name, delta, and pass condition; “underway” is not a fix. If customer screenshots contradict a prior “fixed” update and the request has no verdict, OCR and corroborate them, append one follow-up under the same request ID, avoid repeating verified mutations, correct the internal note, apologize, and keep the case open. Send peer work once with completion watching; after one follow-up, await the event and re-read once. Treat failed reads as unknown and finish with live proof or explicit open owner/status.
5. If no gated remediation exists, create or ID-update one ticket with entity IDs, evidence, outcome, read-back condition, and SLA. Require the returned ID to match the known ID; otherwise report a duplicate end-state mismatch.
6. Send customer updates only when explicitly requested. Re-read authenticated plaintext and answer the latest unmet question with confirmed facts; use the standard two-business-day update window, not an engineering date. For a legal/stage-name consolidation, read both profile claims and independently resolve every linked group/artist ID and name; keep groups separate, verify existing claim evidence before requesting resubmission, and explain that a group claim grants management but no public member link. For a mobile freeze, update/create one handoff after restart/reopen and update checks, ask once for OS/app versions, affected controls, and a screen recording, and never claim recovery without proof. For unclaimed cleanup, preserve the profile, direct the customer to claim it, request exact credits, and treat whole-profile deletion separately after ownership verification. Send through the approved wrapper and require a part ID; after interruption, match the exact outbound body before resending, because an unmatched audit row is unknown.
7. Re-read the live customer-visible surface after the workflow. For an internal summary-and-resolution request, post an Intercom internal note addressed to the requester—not a customer reply—with the symptom, measured state, action taken, proof, and open/closed disposition. When the fix is verified and the customer’s latest message is only thanks or confirmation, state that no further customer reply or catalog action is needed and recommend closing the conversation; do not broaden the resolution into a merge or reopen older requests without separate evidence. Close only when the pass condition is met; otherwise report the exact mismatch (for example, 0/1 corrected), keep the case open, and escalate the unresolved end state with the ticket and conversation evidence.

## Verification

A completed resolution includes either live proof that the requested state landed or an explicit open status with a concrete owner, ticket ID, SLA, customer-reply ID, and failed read-back count. A successful API response or created ticket alone is never proof that customer-visible data changed.
